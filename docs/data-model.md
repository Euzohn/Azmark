# 记录模型与关联设计（提案）

- 状态：部分实现，迁移安全、事务与服务器验收仍需完成
- 最后更新：2026-11-06
- 适用范围：`backend/`、`web/`、AI tool 层、MCP
- 相关规格：`#14` Place、`#15` Trip、`#16` TripItem、`#17` Hotel、`#18` Activity、`#19` Expense、`#21` Note、`#27` Map、`#28` Statistics

> 本文用于指导后续开发。本轮修订已核对现有代码；工作区未找到 `Azmark_行迹_Personal_Travel_OS_方案_v1.1.md`，原规格一致性尚未核验。实施前应补齐规格核验，并同步更新规格或新增 ADR，避免后续开发按旧模型把冗余加回来。下文的“应 / 必须”是目标设计，不能视为已实现。

## 1. 背景与要解决的问题

当前实现中已经出现三类结构性冗余：

1. **地点与活动重复**
   - `TripItem` 同时支持 `place` 和 `activity`；
   - Activity 可以通过 `place_id` 关联地点；
   - 但两者之间没有去重，行程详情会出现「活动卡片 + 同一地点的地点卡片」。

2. **记录价格与开销重复**
   - TransportRecord、Hotel、Activity 都有 `price/currency`；
   - Expense 又有独立的 `amount/currency`；
   - 两者没有关联，也没有统一统计口径，用户可能对同一笔支出录两遍。
   - 当前 `DashboardService.statistics()` 尚无花费汇总；本方案是在建立统一口径，不是在修复已经发生的重复求和。

3. **TripItem 保存了一份重复的时间**
   - Transport、Hotel、Activity 本身已有时间；
   - `trip_items.start_at/end_at` 又保存一份；
   - 通过 `PATCH /trips/{id}/items/{item_id}` 还能直接修改这份时间，容易与源记录漂移。

目标不是把所有实体合并成一张表，而是明确每类数据的职责，让**每类事实只有一个权威来源**。

代码核对还发现：源记录与 TripItem 分别提交事务；网页读取行程会触发交通投影自愈，而 AI 的 `get_trip` 为保持只读只返回交通记录；JSON 导出包含多类实体，但导入仅处理交通记录和行程。这些一致性问题必须随本次模型调整一起处理。

## 2. 分层原则

按职责把数据分成六层：

| 层 | 类型 | 职责 | 是否进行程时间线 |
|---|---|---|---:|
| 事件 | TransportRecord | 航班/火车/其他交通 | 是 |
| 事件 | Hotel | 住宿 | 是 |
| 事件 | Activity | 活动/到访 | 是 |
| 引用 | Place | 地点库、地理引用 | 否 |
| 账务 | Expense | 实际花费 | 否 |
| 内容 | Note / Attachment | 笔记、附件 | 否 |
| 容器 | Trip | 一次旅行的聚合 | — |
| 投影 | TripItem | 时间线成员与排序 | — |

核心原则：

- **时间线只放“什么时候发生了什么”**：Transport、Hotel、Activity。
- **Place 是“在哪里”**，不再自己承担行程归属。
- **Expense 是“实际花了多少钱”**，记录上的 price 只是参考价。
- **Note / Attachment 是内容**，在行程详情中独立分区展示。
- **TripItem 只做排序投影**，不复制权威时间，也不决定成员归属。

## 3. 目标关系

```text
Trip
├── TransportRecord  0..N
├── Hotel            0..N
├── Activity         0..N
├── Expense          0..N
└── Note             0..N

Place
└── Activity         0..N   （活动/到访发生在某个地点）

Transport / Hotel / Activity
└── Expense          0..N   （实际花费来源，可选）

TripItem
└── 只投影 Transport / Hotel / Activity 的成员与排序
```

说明：

- `trip_id` 是行程归属的唯一事实来源。
- `TripItem` 只是时间线展示层；成员关系仍由源记录的 `trip_id` 决定。
- Place 不保存 `trip_id`。
- Expense、Note、Attachment 不进入 TripItem。
- Hotel 和 Transport 暂不强制关联 Place，原因见第 7 节。

### 3.1 引用类型统一规则

新关系使用**实体类型**，交通业务子类型由 TransportRecord 自己提供：

| 用途 | 类型词表 |
|---|---|
| TripItem.item_type | `transport / hotel / activity` |
| Expense.source_type | `transport / hotel / activity`，可空 |
| TransportRecord.type | `flight / train / other` |

因此 Expense 引用一张机票时保存 `source_type='transport'`，由来源记录的 `type='flight'` 决定名称、表单和详情链接，不重复保存交通子类型。

现有 Attachment API 的 `flight / train / transport` 中，`transport` 实际映射 `other`；AI/MCP 的记录写入词表又使用 `flight / train / other`。这些旧词表通过显式适配器映射，不直接作为新关系的内部词表，也不在本次迁移中静默改变旧参数含义。

### 3.2 事务与所有权

- 所有用户数据（包括 TripItem、迁移映射、时间差异档案、导入映射）保留 `user_id`，由服务端认证上下文推导；迁移时从已校验的源记录继承。
- 所有引用必须校验目标存在且属于同一用户；跨用户目标返回 404，不因知道 UUID 而允许关联。多态引用没有普通外键保护，必须通过统一的来源解析器校验。
- **一次业务变更只提交一次事务**：源记录写入/移动/删除、TripItem 同步、关联 Expense 更新，以及对应数据库审计记录一并成功或回滚。
- Repository 的组合操作使用 `flush`，由业务 Service/工作单元控制最终 `commit`；去掉这些路径中嵌套的独立提交。网页、AI 确认执行、MCP 确认执行和导入复用同一业务层。
- 统一锁顺序：先按 ID 排序锁定所有涉及的 Trip，再按 `(类型, ID)` 排序锁定来源记录，最后锁定 Expense/TripItem；操作开始先读取候选 ID，获得锁后重新读取并校验归属，候选集合变化时回滚并有限重试。Trip 删除须在锁住 Trip 后锁定其所有来源；来源绑定、改绑、移动、删除遵守相同顺序。涉及无行程来源时无对应 Trip 锁，但仍须锁定来源并复核。
- Expense 绑定与来源移动/删除须锁定同一来源行，防止并发插入旧行程开销；来源已删除时绑定失败，不产生悬空引用。排序操作同样锁定 Trip，配合唯一约束保证并发写入不产生重复投影。对锁超时、死锁或重试耗尽明确返回可重试错误，不提交部分结果。PostgreSQL 并发行为在服务器环境验证，SQLite 测试只验证业务规则和事务回滚。

当前实现先锁用户行，串行化相关用户写入，尚未实现上述细粒度锁顺序、有限重试及可重试错误映射；不能把 SQLite 测试视为 PostgreSQL 并发验收。

## 4. Place 与 Activity

### 4.1 Place 的定位

保留 Place，作为**用户自己维护的地点库**：

- 字段：类型、国家/省/市/区、名称、本地名称、经纬度、时区、外部 ID；
- 不保存行程归属；
- 不直接成为 TripItem；
- 可被 Activity 引用；
- 地点库继续独立存在，提供搜索、筛选、收藏和未来的地图能力。

Place 类型中的 `airport/train_station/...` 仅表示地点分类，不代表交通记录必须引用 Place。

### 4.2 到访通过 Activity 表达

“把地点加入行程”不再创建 `item_type='place'`，而是创建一条 Activity：

```text
Activity
- type = "visit"
- name = 默认取 Place.name，可修改
- place_id = 目标地点
- trip_id = 目标行程
- start_at / end_at = 到访时间，可空
```

因此：

- “我想去滨海湾花园” = 一条 `visit` 活动；
- “我在滨海湾花园看灯光秀” = 一条 `sightseeing` 活动，关联同一个 Place；
- 地点本身仍然在 Place 库中，不重复进入时间线。

`Activity.name` 保持必填。纯到访时默认使用 Place 名称；这是一个**快照**，之后 Place 改名不会自动改 Activity 名称。

### 4.3 允许同一地点多次到访

**不要对 `(trip_id, place_id)` 做唯一约束。**

同一个地点在同一行程中出现多次是合法场景：

- 机场往返各一次；
- 同一家餐厅吃两次；
- 同一景点白天、晚上各去一次；
- 酒店作为地点，关联多个活动。

需要防的是**同一次事件的重复录入**，不是同一地点出现多次。

规则：

- UI 从 Place 详情“加入行程”时，先展示该行程已有的同地点活动；
- 用户明确选择“新建一次到访”才创建新 Activity；
- AI 在创建前先查询 `search_activities(trip_id, place_id)`，避免重复提交同一次事件；
- 同地点、时间窗口和事件内容相近时提示疑似重复；时间为空只能表示未知，不能视为相同事件的证据；
- 查询去重不能防止网络重试或并发重复提交。创建到访支持用户范围内的幂等键，相同键及相同请求返回原结果，相同键但不同请求返回 409；用户明确新建下一次到访使用新键。幂等记录通过 Alembic 建表，与 Activity 同事务写入；AI/MCP 确认执行使用稳定的动作 ID。

幂等键按 `(user_id, operation, key)` 唯一，保存规范化请求摘要、结果 ID/响应及状态，不保存敏感输入；并发相同键由唯一约束仲裁。有效期至少 90 天，期内即使结果被删除也不得重新创建（返回 409 并提示结果已删除）；过期后不再保证防重。Web 重试复用同一操作键，明确发起新操作时生成新键；不带键的通用 API 请求不承诺防止重试重复，关键界面与 AI/MCP 必须带键。

### 4.4 活动卡片显示地点

行程时间线中的 Activity 卡片必须显示地点信息：

```text
灯光秀
观光 · 9月26日 19:00 · 📍 滨海湾花园
```

地点名称链接到 `/places/{id}`，但不单独生成 Place 卡片。

行程读取返回活动关联的地点摘要（`id/name/localized_name/city`），按当前用户批量查询，避免前端逐卡请求或后端 N+1 查询。Place 删除后保留 Activity 并清空 `place_id`，卡片继续显示活动名称；本期不新增地点历史坐标快照，引用地点的改名/坐标变化会反映到地点摘要。

### 4.5 无时间的到访

如果用户只把地点加入行程、还没安排时间：

- 不强行插入按时间排序的时间线；
- 在行程详情显示为“未安排”，其中 visit 可标注为候选地点；
- 补上时间后进入正式时间线。

所有缺少开始时间的 Transport / Activity 都进入未安排区，包括只有结束时间的记录；保留结束时间并提示补全开始时间。Hotel 的 `check_in` 必填，按日期进入正式时间线。这样不需要额外引入 `TripPlace` 表。

## 5. TripItem 的职责收缩

### 5.1 只允许三种类型

```text
item_type ∈ { transport, hotel, activity }
```

不再允许 `place`。

### 5.2 时间由源实体提供

`trip_items.start_at/end_at` 不再作为权威数据。

时间来源：

| 类型 | 时间来源 |
|---|---|
| transport | `departure_time` / `arrival_time` |
| hotel | `check_in` / `check_out` |
| activity | `start_at` / `end_at` |

Transport 的排序使用计划起止时间；实际起降时间单独展示，不自动覆盖计划时间或改变编排。

时间读取契约：

- `time_kind = instant | date` 区分时刻与日期；未安排由开始值是否为空判断。
- Transport / Activity 使用 `start_at/end_at`（带偏移的 ISO 8601 时刻）；不接受无时区的新增时刻输入。
- Hotel 使用 `start_date/end_date`（`YYYY-MM-DD`），`start_at/end_at` 返回空；不再将 UTC 零点当作真实入住时间。退房日为住宿范围的排他终点，入住和退房日期不随用户时区转换。
- Transport 展示使用各自的 `departure_timezone/arrival_timezone`，缺失时回退到用户时区。
- Activity 新增可空 IANA `timezone` 字段作为事件显示时区。创建时按显式值 → Place.timezone → 用户时区保存；旧数据迁移也按此顺序回填。更新地点不会自动改变已保存时区；只更新时区不改变 UTC 时刻，若要改变当地发生时间，必须同时提交对应时刻。
- 日期分组：Transport 取出发地当地日期，Activity 取事件时区日期，Hotel 直接取入住日期。跨日期的到达/结束信息单独显示。

上述新增字段和回填均通过 Alembic；Web、AI/MCP 与导出格式同步适配，不能只改数据库读取。

`TripItem` 最终保留：

- `id`（稳定的展示条目 ID）
- `user_id`
- `trip_id`
- `item_type`
- `item_id`
- `sort_order`

保留该表的理由是稳定条目 ID、手动编排与同时间条目的顺序；不是用它重复定义成员。目标约束为 `UNIQUE(user_id, item_type, item_id)`，保证同一事件只有一个投影，移动行程时保留条目 ID。收紧约束前先处理历史重复/错误行程投影，并归档原排序。

阶段 4 的 migration `0029_drop_trip_item_times` 删除旧时间列，正常读取与统计不再访问它们。旧版迁移仅归档 place 条目，不能假定所有原始值均已归档；已执行的旧迁移须结合切换前备份核查。

### 5.3 禁止通过 TripItem 改时间

- `PATCH /trips/{id}/items/{item_id}` 不再允许修改 `start_at/end_at`；
- 改时间必须修改 Transport / Hotel / Activity 本身；
- 新契约对旧时间字段返回 422，不得忽略参数后返回成功；
- `TripItem` 只负责展示顺序；调整顺序统一走批量排序接口。旧 PATCH 的 `sort_order` 参数保留为位置调整门面，由同一排序服务移动并重排，拒绝 null/越界位置，不直接写出重复序号。

先完成第 10 节历史时间差异归档与处理，再切换读取；迁移完成后，用单独的 Alembic migration 删除 `trip_items.start_at/end_at`。

### 5.4 统一投影维护与只读查询

当前 `list_items()` 只执行 `ensure_transport_items()`。改造后提供显式修复操作：

```text
ensure_timeline_items()
```

对 transport、hotel、activity 三种类型统一处理：补齐缺失投影，清理源记录已删除或已移出的失效投影，修正错误行程，处理历史重复投影；有效行保留 ID 与手动顺序。修复必须幂等、按用户隔离，写入时遵守事务与并发约束。

正常写入同事务维护投影，旧数据由迁移或显式修复命令补齐。**GET、AI/MCP 的读取不得调用会写库的自愈操作。** 读取以源记录 `trip_id` 为准批量加载成员，投影缺失时仍展示源事件（条目 ID 可空，使用类型+源 ID 作展示键，暂不可重排），过滤错误投影；修复后恢复稳定条目 ID。

阶段 1 是例外过渡：legacy place item 仍是唯一成员/时间来源，只读聚合器保留其旧类型和时间及排序，网页与 AI/MCP 继续展示它；阶段 2 完成转换并切换旧创建门面后才不再返回 place。三类源实体不因该过渡重新依赖 TripItem 时间。

### 5.5 移出行程

TripItem 是投影，不能直接删投影行来表达“移出行程”。

新的语义：

- `DELETE /trips/{id}/items/{item_id}` 表示“把源记录移出该行程”；
- 对 transport/hotel/activity 统一执行：清空源记录的 `trip_id`，再同步删除投影；
- 不删除源记录本身；
- 关联 Expense 同事务移出，`source_*` 仍保留；
- 旧 API 保留为门面，参数始终指 TripItem.id，不能混用源记录 ID。

### 5.6 排序模式与未安排区

Trip 新增 `timeline_order_mode = chronological | manual`，通过 Alembic 迁移：

- 新行程默认 `chronological`；已有行程初始化为 `manual`，保留当前有效条目的相对顺序，避免无法识别历史手动编排时静默改序。
- 两种模式都分为“已安排”和“未安排”，旧行程首次分区时保留各区内部原相对顺序，并归档完整旧顺序。
- `chronological`：先按第 5.2 节定义的事件当地日期分组；每一天先显示酒店日期范围，再显示时刻事件。酒店之间按 `sort_order/id` 排序；时刻事件按 UTC 开始时刻、`sort_order/id` 排序。这是当地日期行程视图，不宣称跨时区全局 UTC 排序。
- 时间模式支持从早到晚或从晚到早；方向作为浏览器本地展示偏好保存，不影响其他设备。降序反转日期及同日时刻，酒店仍在当天时刻事件之前，未安排区始终在末尾；切换手动模式时保留所见顺序。
- 时间模式下，已安排条目只允许在同一日期的酒店组内，或相同开始时刻的事件组内手动调整；不允许拖动绕过时间顺序。未安排区始终可以自由排序。
- `manual`：已安排区和未安排区各自按 `sort_order/id` 排序。修改时间更新显示与分组，但不重新排列区内顺序；跨区移动时追加到目标区末尾。
- 手动模式不再强制按日期分组，以免日期标签打断用户排序；每张卡片显示自己的日期/时区。时间模式按当地日期分组，旧 place 过渡条目按旧开始时刻并使用用户时区归组。
- 提供显式“按时间排列 / 手动编排”切换。切换到手动时以当前展示顺序初始化排序；切换到时间时重新计算时间顺序，界面明确告知顺序会变化。
- 新增/移动到行程的记录在手动模式追加到对应区末尾；时间模式按时间插入，相同时间或酒店组内的新条目追加，未安排条目追加到未安排区末尾。
- 批量排序必须提交完整当前成员 ID 集合（包括两个分区），校验类型、用户、行程、重复项及模式限制；缺失或多余成员返回 409 并要求刷新。投影尚缺失时先显式修复，不在读取中生成。

因此“修改 Activity 时间后立即变化”具体指：时间模式中位置随之变化，手动模式中保留编排；两者都立即更新时间文本和已安排/未安排分区。

## 6. Expense 与记录价格

### 6.1 单一实际花费来源

**Expense 是实际花费的唯一权威来源。**

统计、行程总花费、分类汇总，只读 Expense。

TransportRecord、Hotel、Activity 上的 `price/currency` 保留，但明确语义为：

> 票面价 / 预订价 / 参考价，不参与实际花费汇总。

数据库字段暂不改名；先改 UI 文案和统计口径：

- 记录表单：`票价 / 预订价（参考）`
- 开销：`实际支出`

### 6.2 Expense 增加来源关联

新增字段：

```text
source_type: transport | hotel | activity | null
source_id: UUID | null
```

类型遵守第 3.1 节的实体词表，`transport` 指所有交通记录；交通子类型从来源读取。

约束与索引：

- 数据库 CHECK：两个字段同时为空或同时非空；非空类型只能是上述三种。
- 索引：`(user_id, source_type, source_id)` 用于来源开销查询，`(user_id, trip_id)` 用于行程汇总。
- Service 对创建与 PATCH 合并后的完整状态校验来源存在、类型和所有权，禁止跨用户关联；不能只验证本次提交的局部字段。

允许：

- 一张机票对应多笔开销（票价、行李费、选座费）；
- 一家酒店对应多笔开销（定金、尾款）；
- 一个活动对应多笔开销；
- 完全没有来源的独立开销（餐饮、购物、打车）。

**不强制一对一，也不按金额自动猜来源。**

### 6.3 有来源时行程由来源派生

为了避免出现：

```text
航班属于行程 A
机票开销却属于行程 B
```

规则：

- 有 `source_*` 时，`Expense.trip_id` 是从来源记录派生的**受控冗余列**，用于查询与来源删除后的归属保留，不是第二个可独立编辑的事实；
- 创建/更新时省略 `trip_id` 则派生；显式提供时（包括 null）必须等于来源当前 `trip_id`，否则返回 422；
- 来源记录移动行程时，关联 Expense 同步移动；
- 来源记录被移出行程时，关联 Expense 也移出；
- 无来源时，`trip_id` 由用户手工指定。

完整生命周期：

| 操作 | 来源关联 | Expense.trip_id |
|---|---|---|
| 独立开销绑定来源 | 校验并建立 | 取来源当前行程 |
| 改绑另一来源 | 两字段一起替换并校验 | 取新来源当前行程 |
| 只修改已绑定开销的行程 | 不变 | 仅允许提交与来源一致的值 |
| 主动解绑（两字段显式置空） | 清空 | 默认保留当前行程；可同请求指定合法行程或 null |
| 来源移出行程 | 保留 | 同步置空 |
| 来源删除 | 清空 | 保留删除前行程，见 6.4 |
| 删除 Trip | 保留仍存在的来源 | 源记录、Expense、Note 的 trip_id 一并置空；删除投影，不删除这些记录 |

来源字段只提供其中一个的关联变更请求返回 422；两字段都省略表示不改关联。全部写入入口（包括导入、AI/MCP 确认执行）使用第 3.2 节的同一事务和来源锁，不依赖定时自愈保证账务归属。

### 6.4 来源删除

删除来源记录时：

- 保留 Expense；
- 清除 `source_type/source_id`；
- 保留删除前的 `trip_id` 作为历史快照；
- 之后该 Expense 变成普通的手工开销。

不能复用“先移出行程，再删除来源”的实现，否则会先清空开销的行程，破坏历史快照。删除路径在同一事务中先读取来源当前归属，解绑开销并保留该归属，再删除投影和来源；来源本来无行程则保留 null。

### 6.5 不自动把 price 变成 Expense

创建航班、酒店、活动时，**不默认生成开销**。

改为在记录详情页提供显式操作：

```text
[记一笔开销]
```

点击后预填：

- 金额、币种；
- 分类；
- 行程（从来源派生）；
- 来源记录；
- 日期默认为记账当天，可修改为实际支付日期；不把出发/入住/活动日默认为实际支付日。

并在记录上显示“关联开销 N 笔 / 尚无关联开销”，支持查看已有支出后再新增。关联数量不代表已支付完整金额，也不证明其他独立开销没有重复。创建开销采用与到访相同的用户范围幂等机制，避免点击重试生成两笔。

### 6.6 多币种统计

以 `user.currency` 为报告币种：

1. `expense.currency == user.currency`：使用 `amount`；
2. 否则，如果 `converted_currency == user.currency` 且有 `converted_amount`：使用 `converted_amount`；
3. 否则进入“未换算”分组，不强行加入总额。

页面应显示：

```text
已折算总花费：12,480 CNY
未换算：3 笔（USD / JPY）
```

不能把不同币种直接相加。

补充校验：

- `converted_amount` 和 `converted_currency` 必须成对出现；
- `exchange_rate_date` 依赖 `exchange_rate`；
- `exchange_rate` 如提供须大于 0，表示“1 单位原币兑换多少单位 converted_currency”；提供汇率时必须有换算金额/币种；允许只有手工换算金额而没有汇率；
- 换算允许合理舍入，不做强制完全相等；
- PATCH 校验更新后的完整状态。修改原币金额/币种却未同时提供新的换算字段时，清除旧换算金额、币种、汇率和汇率日期，避免沿用失效结果；
- 历史不完整换算先归档并显式修复；未修复的记录按原币规则处理或列为未换算，不让新增校验导致整个列表无法读取。

金额计算使用 Decimal，汇总由后端按完整筛选集执行，不对前端当前分页求和。用户变更报告币种时重新应用上述规则，原有换算值不被自动覆盖；未换算分组同时展示各原币金额小计。空数据返回零笔/零额，全部未换算时明确显示“可汇总部分为零，另有未换算支出”，不宣称实际花费为零。

### 6.7 退款

当前 `amount >= 0`，模型不支持退款。

本期建议明确不做退款。如果未来需要，新增：

```text
direction = charge | refund
```

统计时 refund 做减项。

**不要用负数金额隐晦表达退款。**

## 7. Hotel、Transport 与 Place 的边界

### 7.1 Hotel 暂不关联 Place

Hotel 已经保存：

- 地址；
- 经纬度；
- 地理编码结果；
- 地图点位。

如果现在增加 `Hotel.place_id`，会立刻引入双位置来源：

```text
Hotel.address / Hotel.lat / Hotel.lon
Place.city / Place.lat / Place.lon
```

因此本期建议：

- Hotel 地址和坐标明确为“预订快照”；
- 可以提供“从酒店保存为地点”，但不自动建立关联；
- 地图继续使用 Hotel 自己的坐标；
- 等确实有“酒店与活动共享同一个地点实体”的需求时，再评审 `Hotel.place_id`，并预先定义位置优先级。

### 7.2 Transport 不关联 Place

交通继续使用：

- IATA；
- 机场/车站文本；
- 现有机场/车站参考数据；
- `origin/destination` 自由文本或代码。

不建议把每次交通起降点规范化为 Place，否则 Place 会膨胀成全球地点库，并与现有参考数据重复。

Place 中的 `airport/train_station/...` 类型仅用于用户收藏。

## 8. Note、Attachment 与未来 Photo

### 8.1 Note

Note 继续作为自由文本内容：

- 可以关联 Trip；
- 不进入时间线；
- 在行程详情独立展示。

如果未来需要“记录级笔记”，复用 Attachment 的 `resource_type/resource_id` 模式，不要同时维护 `trip_id` 和另一套归属。

### 8.2 Attachment

保留现有存储与归属原则：

- 二进制走 StorageProvider；
- 数据库只存元数据；
- `resource_type/resource_id` 作为多态归属；
- 不进入时间线。

当前 AttachmentService 只接受交通记录（`flight/train/transport`，最后一个映射 `other`）。本期行程附件区聚合**当前属于该行程的交通记录附件**，按附件 ID 去重，标明来源记录；不声称已支持直接向 Trip、Hotel、Activity、Place 上传附件。

聚合查询必须同时校验附件与来源记录的 `user_id`；交通记录移出后，附件随来源从该行程聚合视图消失，但不修改附件归属。删除 Trip 不删除交通记录附件。未来扩展附件资源类型时，另行定义来源删除及二进制清理规则，并使用第 3.1 节的类型适配边界。

### 8.3 Photo（未来）

Photo 建议作为 Attachment 的扩展，而不是另起一套记录体系：

- 关联 Trip / Activity / Place；
- 带 `captured_at`、经纬度等元数据；
- 不进入时间线。

本期不实现。

当前决定（2026-11）：Photo 不单独实现。图片通过网页 AI 助手识图提取字段，原图默认不持久化；需要留存的图片走 Attachment（当前支持交通、酒店、活动）。OCR 与独立登机牌解析同理不单独建模块。

## 9. API、AI、MCP 兼容策略

### 9.1 旧 TripItem API

短期保留路由门面，但必须明确这是**语义升级，不是无变化兼容**：

- `POST /trips/{id}/items` 收到 place 请求时，内部创建 `visit` Activity；
- 返回的 `item_type` 变为 `activity`；
- `DELETE /trips/{id}/items/{item_id}` 改为“清空源记录 trip_id”的语义；
- 不再支持通过 TripItem 直接修改源记录时间。

返回 `activity`、Hotel 的日期契约、时间 PATCH 被拒绝以及移出语义都会影响旧客户端。切换时同步更新 Web 类型/调用、AI 工具、MCP 文档和契约测试；发布说明列出变更，不能只保留 URL 就宣称兼容。

旧 place 创建门面使用与新 Activity 创建相同的幂等机制；不再按 `(trip_id, place_id)` 永久拒绝重复到访。长期稳定后再删除该兼容入口。时间 PATCH 禁止写入时启用严格未知字段校验，避免 Pydantic 默认忽略已删除字段。

### 9.2 AI

- `add_place_to_trip` 改为创建 `visit` Activity；
- 创建前查询同行程、同地点活动；
- 不阻止合法的再次到访，但要避免重复提交同一事件；
- `create_place` 只创建地点库条目，不再提示“之后还要加入行程”；
- Expense 支持来源关联，并遵守“有来源时行程派生”的规则；
- 用户只是说“票价多少”时，不自动再建 Expense。
- `get_trip` 使用统一只读聚合器返回交通、酒店、活动（含地点摘要）、未安排分区和排序模式；阶段 3 增加花费摘要及笔记/交通附件分区。不能继续只返回交通记录。
- 查询去重仅提供提示，真正防重依赖确认执行时的幂等键；确认时重新校验来源/行程归属，以当时有效状态执行。

### 9.3 MCP

- Place 仍然是地点库记录，不再有独立行程成员概念；
- Activity 写入支持 `visit`；
- Expense 写入支持来源关联；
- 文档同步说明“实际花费只由 Expense 统计”。
- 读取与网页使用同一聚合规则，无投影补写副作用；写入继续经过绑定当前用户的确认执行层和业务 Service。

### 9.4 规格同步

当前代码和旧提案引用的 `#15/#16` 将 Place 直接列为 TripItem；原规格文件尚未在本工作区找到。实施前应核对原文，更新规格或新增 ADR，明确：

- Trip 可以聚合并展示 Place/Expense/Note；
- 但 TripItem 只表示时间线事件；
- Place 通过 Activity 进入行程；
- Expense/Note 在行程详情独立分区展示。

否则后续开发很容易按旧规格把 place item 加回来。

所有新增界面文案走 `zh-CN/en-US` i18n key；分区、排序切换、重复提示在移动端也须可用，按项目约定使用移动端导航与 Bottom Sheet。本文中的中文文案仅为含义示例。

## 10. 数据迁移

### 10.1 迁移原则

- 所有表结构变更通过 Alembic；
- 本地业务/转换测试使用 SQLite 内存库；PostgreSQL migration、锁与并发验证由服务器环境执行，不在本地启动常驻服务；
- 迁移保守处理历史数据，不猜用户意图；
- 地点本身和实际花费不删除；
- 使用“扩展结构 → 归档/回填 → 切换应用契约 → 最后删列”的分批发布方式。数据转换期间在服务器暂停相关写入，避免旧应用继续产生 place item 或修改旧时间列；
- 数据迁移使用版本内固定的表定义和转换逻辑，不导入会随版本变化的当前业务模型。
- 差异审计和用户处理可提前进行，但旧版本运行期间仍可能产生新差异。服务器切换时暂停相关写入，重新扫描并阻断任何新增未处理差异；确认计数与备份后才切换，部署失败保持旧契约或按备份恢复。

当前 head：`0029_drop_trip_item_times`。

### 10.2 历史时间与排序审计（切换读取前）

新增持久的用户隔离迁移档案与映射表，通过 Alembic 建立；它们只用于迁移追溯/恢复，不参与正常时间线与统计，不能成为新的可编辑事实源：

- 时间/排序档案至少包含 `id/user_id/migration_key/original_item_id`、原行程与引用类型/ID、原始时间与排序、当时源记录时间、差异类型、处理状态和用户选择。以 `(user_id, migration_key, original_item_id)` 唯一，避免重跑重复归档。
- Place 转换映射至少包含 `user_id/migration_key/original_item_id/activity_id`，同样唯一；档案记录转换前的 place item 完整非敏感字段。即使源记录之后被删除，档案也不级联丢失；其引用作为历史标识而非有效业务外键。
- 不记录 PNR、票号、证件号等无关敏感字段。档案保留并纳入备份及用户数据导出；受用户隔离的查询用于差异处理，不把完整用户内容写入日志。

转换前检查：

1. 对 transport/hotel/activity 比较源时间与 TripItem 时间，区分真正差异与格式差异；时刻统一到 UTC 比较，旧 Hotel 按原 `_date_at_midnight` 转换规则比较，不能拿 date 与 datetime 直接比。
2. 对 place item，其时间是历史到访唯一来源，直接完整保留，不能套用“改读源记录”逻辑。
3. 保存所有旧条目的顺序；已有 Trip 初始化为手动模式，保留分区内相对顺序。
4. 对重复投影、错误行程、悬空/跨用户引用、倒置时间窗口生成异常清单；禁止跨用户查找替代来源。无法无损转换的条目先修复，不静默丢弃。
5. 时间存在差异时，提供用户范围内的显式处理：保留源时间，或将合法的旧条目时间写回源记录。选择及两份旧值永久记录在迁移档案中；Hotel 不允许把任意 datetime 自动裁成日期。

**读取切换前须完成所有时间差异的显式选择及阻断异常处理。** 归档不是忽略差异的理由；不能先隐藏旧值，最后直接删列。迁移报告记录各类数量和处理结果供服务器验证。

当前尚无完整的用户范围差异审计和选择工具；迁移阻断不等于差异已解决。不要手工伪造档案或绕过阻断。

### 10.3 Place trip item 迁移

对每条 `trip_items.item_type='place'`：

1. 校验 Place、Trip、条目属于同一用户，并检查转换映射；已转换的条目不重复创建。
2. **默认创建独立 visit，不自动与既有 Activity 合并**。同地点、同时间只生成疑似重复提示；尤其两端时间都为空，不是重复事件的证据。
3. 创建 Activity：
    - `name` 取 Place 名称；
    - `type='visit'`；
    - 保留 `trip_id`、`place_id`、`start_at/end_at`；
    - 按第 5.2 节保存显示时区；
    - 将原 TripItem **原地转换**为 activity 投影，保留条目 ID 与排序。
4. 在同一事务中写入转换映射及原始数据档案；失败整体回滚。
5. 迁移后服务层与数据库类型约束均禁止产生 `item_type='place'`。

用户若事后确认两条是同一次事件，再通过显式合并处理，记录保留项、移除项及关联迁移；本期不提供自动合并，也不依赖额外合并功能才能完成迁移。时间相同或不同的历史事件均不会因相似性被删除。

### 10.4 Expense 迁移

- 新增 `source_type/source_id`、CHECK 与索引，默认来源全部为空；
- 不按金额或描述自动关联历史记录；
- 由用户在 UI 中手工关联；
- 历史换算不完整的数据归档并列出，修复后再收紧相关数据库约束；过渡读取按第 6.6 节容错；
- 花费汇总从此阶段新增，直接读取 Expense，是否关联来源不影响纳入统计。

### 10.5 删除 TripItem 时间列

须同时满足：无旧 place 类型、时间差异已处理并留档、三类投影一致性检查通过、所有入口不再读写旧列、新版关联导出/导入通过往返验证。然后单独迁移删除：

```text
trip_items.start_at
trip_items.end_at
```

不要和 Place 数据迁移放在同一个 migration 里。数据转换后若已经发生新写入，不能盲目 downgrade 把 visit 还原成 place：记录更新可能无法逆推；使用修复性前向迁移，或恢复服务器切换前的完整数据库/存储备份。恢复会涉及切换后写入的取舍，部署说明必须列明。

阶段 4 的 migration `0029_drop_trip_item_times` 单独删除这两列；修订版会阻断未归档条目，但不会追溯影响已经执行的旧版迁移。downgrade 只会重建空列，不会恢复数据，真实回退必须评估切换前备份与切换后的写入。

### 10.6 版本化导出与关联恢复

每个阶段同步调整导入导出，而非最后补齐。当前 v1 格式缺少交通记录稳定 ID，关系主要按 `trip_name` 导出，不能承担完整恢复；新增 v2 关系格式：

- 根对象含 `version`、稳定 `bundle_id`；每个实体带导出 ID，关系使用 ID，不以名称关联。每次生成导出有新的 bundle_id，同一文件重复导入沿用原值。
- 按依赖顺序导入：Trip/Place → Transport/Hotel/Activity → Expense/Note → 排序及迁移档案。Expense 来源必须能解析到前面已导入或已明确映射的实体，Hotel 也必须支持导入，不能遗漏酒店开销的来源。
- 转换映射中的现存目标使用导入 ID 映射；档案中的旧条目 ID、已删除目标 ID 等仅作历史标识保存，标明其属于原 bundle，不能误当成目标数据库的有效引用。导入档案重新归属于当前用户，并以 bundle 命名空间避免历史标识碰撞。
- 目标用户由认证上下文决定，忽略文件中的所有权声明；为目标记录生成新 UUID，通过 `(user_id, bundle_id, entity_type, exported_id)` 唯一的持久导入映射恢复关系。重复导入同一 bundle 及相同内容复用原结果，不重复创建；同一标识下内容变化或已导入实体被删除时返回冲突，由用户显式处理。
- 不同 bundle 不按名称、金额或时刻自动合并。若用户显式将某导出实体映射到现有记录，须校验类型与用户，并让后续引用使用同一映射。
- 保存排序模式、条目顺序、Activity 时区、Expense 来源及换算字段。记录 price 和金额以十进制字符串导出，日期/时刻保留各自类型。
- 每个阶段声明支持的实体与字段：阶段 1 增加 Trip/交通/酒店及排序和档案的 v2 往返，阶段 2 增加 Place/Activity 关系，阶段 3 完成 Expense/Note 关系。导入遇到尚不支持或缺失映射的关系必须明确报错，不得静默跳过；v1 仅保证原有交通/行程导入，额外数组不能被宣称恢复成功。
- 过渡期默认全量导出若包含尚不支持的实体或 legacy place 关系，必须明确拒绝生成可恢复的 v2 bundle；可另提供用户明确选择的部分导出并标注缺失范围，不能称为全量备份。v1 的导入预览对未支持数组列出警告，提交前要求确认，不得静默宣称全部恢复。
- 预览执行完整引用校验；本期 v2 以整个 bundle 为原子导入单位，任一关系失败回滚本次新增业务记录和映射。导入也复用业务 Service，由外层工作单元统一提交。
- 复用方式是各 Service 的 `prepare_*` 阶段：导入与正常创建共用校验/派生（Activity 时区回退、交通座位推断、敏感字段加密、Hotel 状态推断、Expense 来源与行程派生）。引用已由 bundle 解析，导入不再查询尚未落盘的目标行；恢复语义还要保留导出值本身：`occurred_at` 为 null 时仍为 null，显式酒店状态不被创建时默认覆盖。
- Attachment 二进制恢复仍使用数据库+对象存储备份流程；v2 记录 JSON 的往返验收不声称覆盖附件文件。行程附件区聚合规则独立按第 8.2 节验收。

## 11. 实施顺序

### 阶段 0：核验规格与建立一致性基础

- 核验原规格/ADR，确认第 3、5、6 节的类型、排序和生命周期规则；
- 将源记录、投影和相关数据库审计改为同事务写入，统一所有入口；
- 为幂等、迁移档案/映射及排序模式新增 Alembic migration；
- 在服务器生成时间/顺序/引用异常报告，显式处理差异，保存切换前备份；
- 补部分失败回滚、用户隔离及重复执行测试。

### 阶段 1：统一时间、排序与只读投影

- Transport/Hotel/Activity 的时间从源实体读取，加入 date/instant 契约和 Activity 时区；旧 place 条目在阶段 2 前继续使用其原始到访时间；
- 禁止通过 TripItem 改时间，落实时间/手动两种排序模式及未安排区；
- 提供三类投影显式修复操作，GET 不写库；
- 网页、AI/MCP 共用只读聚合器，批量加载三类源实体和地点摘要；
- 同步前端类型/缓存失效、旧接口说明与阶段 1 的 v2 导入导出；
- 补时间差异处理、跨时区、酒店日期、排序模式、缺失投影及只读测试。

### 阶段 2：Place → visit Activity

- Activity 增加 `visit` 类型；
- 按第 10.3 节逐条转换 legacy place item，保留条目 ID、排序、映射，不按相似性合并；
- Place 加入行程改为幂等创建 Activity，展示同地点已有活动；
- 活动卡片显示地点链接和事件当地时刻；
- 同步 Web、AI、MCP、旧 API 门面及 Place/Activity v2 关系导入导出；
- 补同地点同时间/空时间事件保留、重复到访、重试幂等、迁移重跑及关联恢复测试。

### 阶段 3：Expense 关联与统计

- Expense 增加来源约束、索引、统一解析器和并发锁；
- 在同事务中实现绑定、改绑、解绑、来源移动/移出/删除及 Trip 删除；
- 记录详情增加幂等“记一笔开销”与关联开销列表；
- 行程详情增加花费、笔记及当前交通附件聚合区；
- 统计按报告币种汇总，未换算单列；
- 同步 AI/MCP、前端缓存失效、Expense/Note v2 导入导出；
- 补完整生命周期、跨用户来源、失败回滚、分页外汇总、多币种及关系恢复测试；服务器验证 PostgreSQL 并发绑定与移动/删除。

### 阶段 4：最终收缩与验收

- 检查迁移档案、关联完整性、v2 往返结果及服务器迁移验证报告；
- 满足第 10.5 节前置条件后，单独删除 `trip_items.start_at/end_at`；
- 清理旧 place item 的存储逻辑和失效断言，保留迁移/兼容契约回归测试与迁移档案；
- 同步 API、部署与恢复文档。地图增强、Hotel.place_id、通用附件归属扩展另行评审。

## 12. 验收标准

完成后应满足：

- 时间线只出现 Transport / Hotel / Activity；
- 不再出现 `item_type='place'` 的 TripItem；
- 同一行程可以在不同时间多次到访同一 Place；
- 同地点同时间（包括两端时间为空）的 legacy place item 与 Activity 仍分别保留，除非用户明确进行后续合并；
- 迁移保留旧条目 ID/顺序/时间档案与转换映射，重跑不重复创建；异常引用不会被静默丢弃或关联到其他用户；
- 读取切换前完成时间差异显式处理，删列后原始值仍可追溯；
- 活动卡片能显示并跳转关联地点；
- 地点删除保留活动及名称，清空地点关联；
- 时间模式修改 Activity 开始时间后按规则重新定位；手动模式保留区内编排，两者都立即更新显示和未安排分区；
- Hotel 日期不伪造成 UTC 时刻；Activity 时区、跨日事件及只有结束时间的条目均遵守第 5 节契约；
- 不能通过 TripItem API 把活动时间改成与 Activity 不一致；
- GET、AI/MCP 只读请求不产生数据库写入；投影缺失仍能显示源事件；
- 同一来源只有一个投影，移动行程保留条目 ID；错误/重复/缺失投影可幂等修复；
- 来源、投影、关联开销及对应数据库审计任一步骤失败时整体回滚；
- 记录上的 price 不进入总花费统计；
- 创建记录不会因为填了 price 就自动生成 Expense；
- 一条来源记录可以关联多笔 Expense；
- 来源记录换行程后，关联 Expense 的行程同步变化；
- 来源记录删除后，Expense 保留在原行程，但来源变空；
- 绑定、改绑、主动解绑、移出行程、删除 Trip 按生命周期表执行；跨用户来源返回 404；
- 并发绑定开销与移动/删除来源不会产生悬空或归属错误的开销；
- 到访/开销的同键重试不重复创建，显式新建仍允许多次到访和多笔开销；
- 多币种开销不会被直接相加，未换算部分单独显示；
- 金额/币种变更不会沿用失效换算，汇总覆盖完整筛选集而非当前分页；
- 行程详情明确区分“时间线 / 未安排 / 花费 / 笔记附件”，移动端与双语文案可用；
- 附件区只聚合当前行程内交通记录的附件，去重且标注来源，移出记录后聚合结果随之更新；
- AI 不再生成 place 类型的时间线条目；
- Web 与 AI/MCP 读取的成员/顺序/摘要口径一致，成员或开销变更后相关前端缓存失效；
- v2 导出再导入后 Trip、Transport、Hotel、Place、Activity、Expense、Note 的关系及排序/时区/迁移档案能恢复；重复导入相同 bundle 不新增记录，缺失关联明确报错；附件二进制由备份恢复单独验证。

## 13. 明确不做的事

以下方案不建议采用：

1. **不把所有类型合并成一张通用 Record 大表**：会失去字段约束和业务语义。
2. **不对 `(trip_id, place_id)` 做唯一约束**：会阻止合法的重复到访。
3. **不让 Place 直接成为 TripItem**：会造成活动和地点重复。
4. **不让 Expense 和记录 price 各自独立统计**：会形成两个总花费。
5. **不自动把 price 转成 Expense**：票面价不等于实际支出。
6. **不按金额自动关联历史 Expense**：容易错误归因。
7. **不让 TripItem 保存权威时间**：会持续产生同步和漂移问题。
8. **不把 Expense/Note 塞进时间线**：行程详情应分区展示。
9. **不把交通起降点全部规范化为 Place**：会与现有参考数据和 IATA 体系重复。
10. **不凭同地点同时间自动合并历史事件**：相同时间或空时间不能证明同一次事件。
11. **不把只读自愈当作一致性保证**：正常业务通过同事务写入，历史数据显式修复。

## 14. 决策记录摘要

| 决策 | 结论 |
|---|---|
| Place 是否保留 | 保留，作为地点库与地理引用 |
| Place 是否进入时间线 | 否，通过 Activity 表达到访 |
| 同一地点能否多次到访 | 可以，相似事件只提示；用幂等键防重试，不按地点去重 |
| TripItem 类型 | 仅 transport / hotel / activity |
| TripItem 是否保存时间 | 否，时间由源实体提供 |
| TripItem 保留理由 | 稳定条目 ID、手动编排、同时间顺序；成员来自源记录 |
| 排序规则 | 新行程默认时间模式，旧行程保留手动模式；未安排单独分区 |
| Hotel 时间 | 日期范围，退房日排他；不制造入住时刻 |
| Activity 时区 | 保存事件显示时区，地点变化不自动改动 |
| 历史 place 迁移 | 逐条转 visit，保留 ID/顺序/映射，不自动合并 |
| 历史时间差异 | 切换读取前显式处理并持久归档 |
| 记录 price 的角色 | 票面/预订参考价，不参与花费统计 |
| Expense 的角色 | 实际花费唯一来源 |
| Expense 来源关联 | 可选，多对一，不自动创建 |
| Expense 来源类型 | transport / hotel / activity；交通子类型从来源读取 |
| 有来源 Expense 的行程 | 从来源派生并同步 |
| 来源删除后的 Expense | 保留，清除来源，保留行程快照 |
| 主动解绑 Expense | 默认保留行程，可显式改为合法行程或空 |
| 删除 Trip | 保留源记录/开销/笔记，清空其行程，删除投影 |
| 一致性保障 | 业务层单事务、来源锁、唯一约束及幂等键 |
| 读取与修复 | 只读聚合无写入；缺失/失效投影显式修复 |
| Hotel/Transport 与 Place | 暂不强制关联 |
| Note/Attachment | 不进入时间线 |
| 本期行程附件区 | 聚合现有交通附件，不新增通用上传归属 |
| 关联导入导出 | v2 稳定 ID 与用户隔离映射，随阶段交付 |
